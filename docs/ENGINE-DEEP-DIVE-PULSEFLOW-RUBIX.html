PulseFlow & Rubix — Engine Deep Dive

A technical deep dive into the two deterministic engines that power the AWS System Design Simulator: PulseFlow, the reactive traffic-and-failure simulation engine that re-evaluates the entire architecture graph every 180 ms, and Rubix, the declarative rule engine that grades user-drawn architectures against design challenges in real time.

1 · Why Two Engines Exist

Most system-design learning tools are either static diagramming canvases (no feedback at all) or cloud calculators (cost only, no behavior). The simulator needed two things neither provides:

  • Time-domain behavior — what actually happens to a real architecture over time when demand exceeds capacity: queues build, latency compounds, connection pools exhaust, services collapse, and replacement capacity boots. A static "utilization %" label cannot teach this. PulseFlow was built to make saturation dynamics observable, tick by tick.
  • Objective, instant grading — a way to score a user-drawn architecture against a design challenge deterministically, offline, and in real time, without shipping designs to an LLM or a backend. Rubix was built as a declarative rule engine so that challenges are pure data (JSON), not code — new challenges require zero engine changes.

Shared design constraints

  • Deterministic. Same graph + same config ⇒ same outcome. This is what makes the behavioral benchmark (and regression testing) possible at all. The only randomness is opt-in variable client traffic — bounded random-walk sampling.
  • Fully client-side. Everything runs in the browser at interactive rates. No inference calls, no server round-trips between "user drags a slider" and "the system reacts."
  • Data-driven. Service behavior lives in JSON specs, not engine branches. The engine implements classes of behavior; the data assigns each of the 74 catalog services to a class.

2.2 The tick pipeline — 8 stages every 180 ms

  1. Backpressure pass — from the previous tick's state, every request-holding node sums the latency of its synchronous dependencies (weighted by call share) and the fraction of its calls aimed at offline dependencies. Chains propagate one hop per tick, so a slow database ripples up through the app tier to the gateway over a few ticks — exactly like a real cascading brownout.
  2. Variable-traffic sampling — every 6 ticks (~1 s), clients with variable traffic sample a new RPS from their configured band; the realized mean is written back on pause/stop so the cost panel reflects what actually ran.
  3. Topological ordering — Kahn's algorithm orders producers before consumers so each node sees its full upstream demand in a single pass, with a deterministic fallback for cyclic graphs.
  4. Offline recovery check — a collapsed node restarts only after the capacity its current configuration would provide covers demand with ≥10% headroom for 10 consecutive ticks (~1.8 s) — modeling replacement instances booting after a scale-out or a load drop.
  5. Capacity resolution — a strict 5-level precedence decides each node's ceiling (§2.3).
  6. Metrics + health resolution — demand vs. capacity settled through one of three saturation branches (§2.4), producing all 10 per-node metrics and a health state.
  7. Output propagation — processed traffic fans out across outgoing edges honoring per-edge traffic weights, cache hit-rate offload (CloudFront / ElastiCache / API Gateway cache), and a CDN attenuation factor; edge glow intensity is computed against the target's real capacity, not its raw knob.
  8. Offline cascade — a BFS from every live client marks reachability; any subgraph cut off by an offline node is starved (zeroed), so a dead load balancer correctly takes its whole downstream tree dark while an alternate live path keeps its branch alive.

The coupling that creates emergent backpressure: formulas use effective latency — the node's own service time plus the wait inherited from slow synchronous dependencies: Teff = L + Σj wj · min(Lj, 6·104). That is what makes a slow RDS exhaust its EC2 callers' concurrency: the caller's capacity formula divides by a growing request time, so its ceiling drops tick by tick while the database struggles. Backpressure is not a scripted animation; it falls out of the math.

2.4 Three saturation behaviors

ClassServicesBehavior past capacity
reject33Managed-quota throttling: 100% of the excess fails immediately (429/ThrottlingException), no backlog, accepted requests stay fast, recovery is instant when load drops — the defining behavior of AWS managed services (API Gateway, SNS, Cognito, KMS, Bedrock…).
queue9Buffering services (SQS, Kinesis, Batch, Glue, MediaConvert…): excess work backlogs instead of erroring; producers never fail. Health signal = backlog age, with a deep 60-ticks-of-capacity buffer — buffering is the entire point of these services.
degrade16Resource-bound services (EC2, ECS, RDS, ElastiCache, OpenSearch…): below saturation, latency follows an M/M/1-style queueing curve — base × ρ²/(2(1−ρ)) — the hockey-stick that makes 85% utilization visibly slower than 50%. Past saturation, a compounding penalty (seed 12 ms/tick, ×1.12 acceleration) escalates latency toward the request timeout; at the timeout in-flight requests are shed; after 6 sustained overloaded ticks (~1.1 s) past the service's offlineAtRatio (1.4–1.6×), the node collapses offline. When relieved, the penalty decays at 0.6/tick — recovery is visible within ~1 s.
Latency vs. utilization — the two regimes of a resource-bound service

Below saturation, wait time follows the M/M/1 curve — near-flat until ~70% utilization, then the hockey-stick. At ρ = 1 the model hands over to the per-tick compounding penalty, which escalates latency toward the 60-second timeout; sustained residence past ρ* collapses the node offline.

Failures don't stop at the failing node: calls routed into an offline synchronous dependency fail at the caller, and async targets (SNS, EventBridge, CloudWatch, queue-class services, control plane) are correctly exempt from backpressure inheritance — decoupling producers from slow consumers is what queues are for, and the engine honors that.

2.5 Crash and recovery lifecycle

normal → busy (ρ>0.78) → overloaded (ρ>1.12) → failing (ρ>1.4) → OFFLINE after 6 sustained ticks past offlineAtRatio (~1.1 s) → recovery once demand ≤ 90% of would-be capacity for 10 ticks (~1.8 s) → normal (metrics reset, streaks cleared)

Collapse and recovery are streak conditions, not instantaneous flips — 𝟙[·] is the indicator over consecutive ticks:

13offline ⇐ Σt 𝟙[ ρt > ρ* ] ≥ 6,   ρ* ∈ [1.4, 1.6]sustained collapse · ≈ 1.1 s @ 180 ms tick
14normal ⇐ Σt 𝟙[ λt ≤ 0.9 C ] ≥ 10recovery · replacement capacity boot · ≈ 1.8 s

The health state machine resolves from 8 thresholds over CPU pressure, error rate, and overload ratio, then clamps by class: throttle/none services can never show failing/offline (they shed load and stay up), while offline-class services surface stress before collapsing. Queue caps (8 ticks of capacity for request-path services) bound backlog growth so a relieved node recovers promptly instead of draining an unbounded fantasy queue.

2.6 The Dynamic RPS auto-sizer

PulseFlow also runs in reverse. estimateDemand() propagates every client's request rate through the graph topologically (traffic weights, CDN factor, cache-hit offload) to compute the arrival rate each service must absorb — then autoSizeForDemand() inverts each capacity formula to emit the config that carries that demand at 65% target utilization: ECS task counts, ASG sizes, Lambda concurrency, read-replica counts, DynamoDB RCU/WCU (with item-size rounding), Kinesis shards. One click sizes an entire architecture the way a capacity-planning spreadsheet would — using the same formulas the simulation enforces, so the sized system actually holds up under the simulated load.

2.7 How it was calibrated

PulseFlow's constants weren't guessed once and frozen. The engine is wrapped by a benchmark harness that drives every catalog service through a standardized deterministic scenario suite — UNDER (ρ=0.5), NEAR (ρ=0.92), OVER (ρ=1.6/2.0), RECOVER (ρ=0.3) — and scores observed behavior against the documented AWS saturation semantics for that service's class: fail-fast services must show flat latency and instant recovery; queues must show backlog-age growth and zero producer errors; resource-bound services must show the queueing hockey-stick, ≥3× latency escalation, then collapse.

Current result: 453/453 checks passed — 100% behavioral accuracy across 73 benchmarked services (see the Simulation Accuracy Benchmark report). This harness is what turned early knob-driven behavior — where the user's throughput setting silently was the capacity — into today's quota/formula model: the harness made the unrealistic cases measurable, and the engine was reworked until they passed.

3.2 Why declarative

The alternative designs were (a) hand-coded validation per challenge — unmaintainable, or (b) LLM review — non-deterministic, slow, online-only, and impossible to run on every canvas mutation. Rubix instead defines a tiny JSON rule grammar and one pure evaluator. A challenge is entirely data:

{ "kind": "hasService", "anyOf": ["elastiCache"], "mustBeConnected": true }
{ "kind": "hasEdge", "fromAnyOf": ["apiGateway"], "toAnyOf": ["lambda"] }
{ "kind": "noOverload" }
{ "kind": "allOf", "rules": [ ... ] }

The evaluator is pure and deterministic, with a TypeScript exhaustiveness guard so a new operator cannot be added to the grammar without being handled. Adding a challenge means writing JSON (validated by a schema script in CI), never touching the engine.

3.3 The insight that makes grading honest: reachability

A service only counts if it's actually wired into the request path. Before any rule evaluates, Rubix runs a BFS from every client node following allowed connection direction, producing the reachable set — hasService rules with mustBeConnected filter against it. Dropping an ElastiCache node on the canvas next to your architecture earns nothing; wiring it between the app tier and the database does. This closes the "decorative architecture" loophole that a naive node-count grader would reward.

3.4 Live coupling to PulseFlow

Rubix's noOverload operator reads the live health states PulseFlow computed — a node in overloaded, failing, or offline fails the check. This is where the two engines compose: a challenge can require not just the right shape (services + edges) but the right sizing — the design must actually survive the simulated load. All ten authored challenges use it. Grading re-runs on every canvas change, so milestones toast the moment the graph earns them, with completed-challenge downgrade protection so loading a blank canvas can't silently revoke progress.

3.5 Scoring model

17S = 100 · Σpassed wiΣmandatory wj,   pass ⇔ S ≥ 70weighted rubric · optional bonuses permit S > 100
18ℛ = BFS(clients);   counts(s) ⇔ s ∈ ℛreachability gate · wired, not decorative
19noOverload ⇔ ∀ n : σ(n) ∉ { overloaded, failing, offline }live coupling · Rubix reads PulseFlow health states
  • Each of the 95 checks carries a weight (1–3); failed mandatory checks return their authored failHint.
  • The score normalizes earned weight against mandatory weight only — so the 20 optional bonus checks (read replicas, multi-AZ patterns, cache layers…) can push a score above 100%, rewarding best practices without punishing their absence.
  • Pass = score ≥ 70. Milestones are evaluated in the same pass from the same reachability set, so the rubric and the milestone tracker can never disagree about the graph.
  • Hints are revealed against the first missing milestone — the engine computes exactly which gap the user should close next, rather than dumping a hint list.

The reviewer sits behind a strategy interface (ArchitectureReviewer), with an AiReviewer seam already reserved: the long-term plan is hybrid review — Rubix for deterministic structural truth, an LLM for qualitative critique — without touching any caller.

3.6 The third layer: topology compliance

Below the challenge rubric sits an always-on compliance engine that governs what can be drawn at all: 456 port-typed connection rules generated from the 74-service catalog. Every attempted edge is validated for direction (output→input), self-loops, duplicates, port-type compatibility, and semantic legality — a client cannot connect straight to an internal database node, and a VPC boundary only accepts the 19 service types that can actually live inside a VPC. Illegal edges are rejected at draw time with an explanation, which means Rubix's grading rules never need to police physically-impossible graphs; the compliance layer already guaranteed structural sanity.

4 · How the Engines Compose

Engine Composition & Execution Flow

One graph, four consumers, zero servers. The layering is strict: compliance guarantees structural sanity so grading rules stay small; simulation computes behavior so grading can assert on performance, not just shape; and cost reads the same config the simulation validated, so the bill and the behavior can never describe two different systems.
